# MEDCHAIN Comprehensive Threat Model

This document identifies potential security threats, attack vectors, defensive controls, and residual risks across the MEDCHAIN architecture.

---

| Threat ID | Threat Category | Attack Scenario | Impact | Mitigation Strategy | Residual Risk |
|---|---|---|---|---|---|
| **TM-01** | Unauthorized Doctor Access | A registered doctor attempts to query records of a patient without active consent. | Breach of clinical confidentiality. | Strict API and database check against `ConsentGrant` validating `isRevoked=false` and `expiresAt > NOW()`. Zero wrapped keys exposed. | Minimal; server code defects could cause bypass if authorization layer is skipped. |
| **TM-02** | Malicious Patient Manipulation | Patient attempts to forge medical diagnoses or doctor signatures. | Fraudulent clinical history. | Attending physicians digitally sign clinical records using Ed25519 keypairs anchored on Ethereum smart contracts. | Patient can upload arbitrary unverified personal documents; hospital portal clearly tags records as self-reported vs. verified provider-authored. |
| **TM-03** | Compromised Application Server | Attacker gains remote shell access to the Next.js backend node. | Potential compromise of non-sensitive metadata, session tokens. | Application server does NOT hold patient private keys or plaintext DEKs. All records in transit and at rest are encrypted. | Attacker could monitor future incoming traffic or modify client code delivered to browsers if subverted. |
| **TM-04** | Compromised SQLite Database | Database file is extracted or dumped via SQL vulnerability. | Leaked user accounts, wrapped keys, and non-sensitive metadata. | Plaintext documents and plaintext keys are never stored in the database. All DEKs are wrapped with AES-KW/RSA. Password hashes use salted bcrypt (cost 10). | Attacker could analyze access logs and metadata to infer medical visit frequencies. |
| **TM-05** | Unauthorized IPFS Retrieval | Attacker obtains the IPFS CID of a patient record and downloads the raw file. | Download of encrypted binary blob. | All documents are encrypted with AES-256-GCM before CID generation. Raw IPFS content is cryptographically indistinguishable from random bytes. | Public CID could leak file sizes and upload timestamps. |
| **TM-06** | Metadata Leakage | Traffic analysis or blockchain monitoring exposes patient disease categories. | Privacy degradation via side-channel inference. | Category names and record details are hashed on-chain (`bytes32 metadataHash`). Public blockchain transactions only reveal pseudonymous Ethereum addresses. | Advanced traffic analysis could correlate transaction timings with doctor clinic hours. |
| **TM-07** | Malicious File Upload | Attacker uploads malware disguised as a PDF or imaging report. | Potential client-side execution if viewed unsafely. | Files are validated by MIME type, size bounds, and sanitized during preview. PDFs are previewed inside isolated sandboxed iframes. | Zero-day parser vulnerabilities in client PDF viewers. |
| **TM-08** | Replay Attacks | Attacker intercepts a consent grant transaction and replays it. | Unauthorized extension of expired access. | Smart contracts track nonces, monotonic sequence numbers, and strict UNIX timestamp expirations. | Minimal; EVM transaction nonces inherently prevent transaction replays. |
| **TM-09** | Permission Escalation | Doctor granted access to lab reports attempts to query psychiatric notes. | Violation of granular consent bounds. | Resource-level filtering checks record category against `ConsentGrant.categories` JSON array and smart contract scope mask. | Logic bugs in category filtering algorithms. |
| **TM-10** | Key Compromise | Patient loses or leaks their private decryption key. | Total compromise of that patient's historical records. | Key rotation and recovery mechanisms. Multi-factor protected encrypted key backups. | Historical records encrypted with the compromised key remain vulnerable if downloaded prior to rotation. |
| **TM-11** | Stolen Sessions | Attacker intercepts JWT bearer token via cross-site scripting (XSS). | Impersonation of patient or doctor until token expiration. | Short-lived JWT expiration (configured in env), secure cookie configuration, and CSP headers mitigating script injection. | Session hijacking remains viable during the active token validity window. |
| **TM-12** | Blockchain Tx Manipulation | Malicious miner attempts to alter record registration on-chain. | Falsified record timestamp or hash. | Ethereum consensus and proof-of-work/stake immutability. | 51% attack on local/private chain if network has insufficient distributed hashing power. |
| **TM-13** | Denial of Service (DoS) | Attacker floods upload or verification endpoints with dummy files. | Service degradation for legitimate patients. | Rate limiting middleware, maximum payload bounds (10MB limit), and Zod input validation prior to cryptographic processing. | Resource exhaustion on client device if processing very large local files. |
| **TM-14** | Data Integrity Attacks | Attacker alters a byte in the encrypted file stored on IPFS or local disk. | Delivery of corrupted clinical records. | Integrity verification recomputes SHA-256 fingerprint upon retrieval and compares against immutable on-chain hash. Altered payloads are rejected immediately. | Patient cannot view corrupted file unless backup version is restored. |
| **TM-15** | Insider Misuse (Hospital Staff) | Authorized clinic staff downloads patient records and shares them outside system. | Clinical data exfiltration. | Comprehensive access logging records actor ID, timestamp, and IP address for every decryption event on the immutable `AuditRegistry`. | The physical limitation of cryptography: once plaintext is displayed on a screen, the system cannot prevent external photography or manual transcription. |
